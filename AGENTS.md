## Plan corrections (Group 9, npm launcher): the plan text is wrong or incomplete in several places

Group 9 (Tasks 9.1–9.2) — `npm/matrix-workspace-tui/` (package.json, index.js, scripts/platform.js, scripts/download.js, test/*.test.js) is authoritative; the plan text is stale or un-runnable in several places, all corrected during implementation:

- **The plan's download tests deadlock as written**: `runDownload` used `spawnSync`, which blocks the test process's event loop — but the static HTTP server lives in that same process, so it can never answer the child's requests and the child hangs forever (this wedged the run for ~75 min). Fix: `runDownload` now uses async `spawn` + a Promise resolving `{status, stdout, stderr}` (event loop free to serve HTTP while the child runs), and the idempotent test `await`s the first `runDownload` (otherwise both runs race and the `hits.binary === 1` assertion flakes).
- **`fetchBinary` had no timeout** (supervisor-required fix): `postinstall`/download against the real GitHub URL — which has no release until Group 10 publishes one — could hang forever. `fetchBinary` now does `request.setTimeout(MATRIX_WORKSPACE_TUI_DOWNLOAD_TIMEOUT_MS || 30000)` + `request.destroy(err)` so the error path rejects cleanly, and `main`'s catch `rmSync`s `BIN_DIR` so no partial tmp/checksum/dir is left behind (this also makes the plan's "no partial binary left behind" assertion actually pass — with plan-literal code, `bin/` survives a checksum-mismatch failure because the `.sha256` file was written there). A fourth download test covers the timeout path (server holds the connection open, 500ms timeout, asserts non-zero exit + `/timed out/` + no `bin/`). The `bin/` dir is now in `.gitignore`.
- **`package.json`'s `"test": "node --test test/"` is broken on Node 26** (the only Node on this machine): newer test runners treat the directory arg as an entry module → `MODULE_NOT_FOUND`, zero tests run. Changed to `"test": "node --test"` (bare; auto-discovers `test/*.test.js`, works Node ≥ 18). Acceptance criterion is bare `node --test`, which passes: launcher 2 + download 4 = 6 tests green.
- Test count: plan says `# pass 5` (2 launcher + 3 download); actual is 6 (the added timeout test). The download tests need `server.close()` to destroy tracked sockets first (`closeAllConnections`-style), otherwise `close()` waits on the never-answered connection.
- **The package is scoped `@abderrazzakchabab/matrix-workspace-tui` since v0.1.1** (PR #14): the v0.1.0 publish failed with 403 because the captain's npm token only covers `@abderrazzakchabab` packages. `publishConfig.access: public` stays (scoped packages default private). Never unpublish/republish the unscoped `matrix-workspace-tui` name — only the scoped name can be published with this token.
- **v0.1.2 added proxy support to `download.js`**: Node's `https.get`/`http.get` ignore the conventional proxy env vars, so install-time downloads stalled on corporate networks (this machine's Fortinet proxy blocks direct TLS to github.com; curl works). `resolveProxyFor(url)` (exported for unit tests; `require.main === module` guards `main`) honors `HTTPS_PROXY`/`https_proxy`/`HTTP_PROXY`/`http_proxy`/`NO_PROXY`/`no_proxy` with curl/npm semantics (`*`, exact host, subdomain, leading dot, optional port, IPv6 brackets), returns an `https-proxy-agent`/`http-proxy-agent` instance or null, and is lazy-required so the script runs without deps. Deps: `https-proxy-agent` ^7.0.6 + `http-proxy-agent` ^7.0.2 (v7 = CJS, Node ≥ 14; v9 requires Node ≥ 20 — do not bump). The `files` list is unchanged (deps install from the registry). Suite is now 19 tests: 4 download + 2 launcher + 13 proxy.
- **v0.1.3 added redirect following to `fetchBinary`** (branch `fm/matrix-tui-rel-003`): Node's core `http`/`https` client does NOT follow redirects, and GitHub release downloads ALWAYS answer 302 to the objects.githubusercontent.com CDN — so `npm install @abderrazzakchabab/matrix-workspace-tui` (postinstall download) failed with `Download failed: 302` once v0.1.2's proxy support let the request actually reach GitHub. `fetchBinary` now follows 301/302/303/307/308, bounded to `MAX_REDIRECTS = 5`, resolving `Location` against the current URL via `new URL(location, currentUrl)` (RFC 7231; GitHub sends absolute CDN URLs but relative/scheme-relative must resolve too). Every hop re-runs `resolveProxyFor(currentUrl)` so NO_PROXY is evaluated per host (the CDN host differs from github.com), re-applies `request.setTimeout(TIMEOUT_MS)`, and keeps the same non-200 / invalid-Location / too-many-redirects clean-failure paths (main's catch rmSyncs BIN_DIR). The `startServer` test helper gained a `redirect` option that answers 302 → `/real/<...>` for both asset paths; the regression test asserts both downloads were redirected, the binary lands, and the checksum verifies. TDD: that test fails with `Download failed: 302` against the v0.1.2 code. Suite is now 20 tests.
